Security Assertion Markup Language (SAML) is an open, XML-based standard used for exchanging authentication and authorization data between an Identity Provider (IdP) and a Service Provider (SP) to enable Single Sign-On (SSO).
PingDS (Directory Services) and PingIDM (Identity Management) are distinct components of the Ping Identity platform with different core functions. PingDS serves as the backend directory and repository, storing identity data and handling LDAP operations, whereas PingIDM manages the full identity lifecycle, including workflow-driven provisioning, synchronization, and access management.

What it is
  - The standard (SPEC.md): LDAP's own schema format (RFC 4512), extended through
    LDAP's official X- mechanism. Every attribute declares whether it moves as-is,
    must stay stable (names and URLs other parties use), is rewritten per cloud,
    is a secret reference, or is measured from the live system. So the schema
    itself says what a migration touches. Postgres enforces ten rules, including
    three LDAP doesn't guarantee: references must point at real entries, every
    write needs an approved change record, and every change is kept in history.
  - Synthetic estate: 229 fictional entries ("Example Aero") with problems planted
    for the tools to find.
  - Renderer: reads the database and writes Terraform (AWS or Azure), a dsconfig
    batch file, DS setup scripts, ACI LDIF and PingFederate config. You change an
    entry, not a file.
  - Planner: compares two environments and lists blockers and dated actions, each
    with an owner.

  What the demo shows
  1. Same databases, two clouds. The DS and PingFederate config comes out
     byte-identical for AWS and Azure. Only the Terraform and per-server setup
     scripts differ.
  2. The Azure servers join the existing directory deployment by pulling from the
     AWS servers, so encrypted data and backups stay readable.
  3. Seven blockers found, including a changed LDAPS name, missing firewall rules
     and backup, untested or unowned consumers, and certificates expiring before
     cutover.
  4. Two approved changes (two database entries) produce exactly one new firewall
     rule and one DNS fix, and the blockers drop from 7 to 5.
  5. The database rejects an unapproved change, deleting a certificate still in
     use, a password pasted where only a reference belongs, and an entry missing a
     required field.

  A flaw the build exposed: adding one Azure firewall rule at first renumbered the
  priorities of three unrelated rules. In production that's needless Terraform
  churn. The fix was to store the priority in the database as a fixed value. The
  lesson for the standard: cloud-specific settings are pinned in the data, never
  calculated at render time.
