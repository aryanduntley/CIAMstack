# CIAMstack reports in detail

Every question the record answers, with what each command shows and what the planner (`opsdir plan`) does with it. The [README](../README.md#answer-operational-questions-in-seconds) has the short version.

| Question | Command |
|---|---|
| What expires soon? | `opsdir report expiring` |
| What breaks if this certificate expires or is replaced? | `opsdir report blast-radius <certificate DN>` |
| What does rotating this key or secret touch? | `opsdir report rotation-impact <credential DN>` |
| What does this application touch, across every product and cloud? | `opsdir application <name or DN> [--env <env>]`: its identity (integration), directory consumer and ACIs, service names, secrets and keys (references only), certificates with expiry, network rules and allowlists, monitors and synthetic checks, changes and incidents, and owners, each row naming the entry it comes from (`--format json` for tools); an application (`ciamApplication` under `ou=applications`) groups the entries it is made of, and any other entry is a view of itself |
| What depends on this, and what does it depend on? | `opsdir graph <name or DN> [--direction up\|down\|both] [--depth N] [--env <env>] [--format text\|json\|dot]`: references by DN and by role (bound per environment), as a tree, JSON or Graphviz DOT |
| The estate in numbers | `opsdir summary [<from> <to>]`: applications, integrations, consumers, expiring certificates, pending changes, incidents and entries awaiting an import, each count with its evidence; with two environments the plan's blockers, actions and ok lines. Counts only, no scores |
| Where does each environment keep its keys and secrets, and correctly? | `opsdir report keys <env>`, `opsdir report credentials` |
| Who can read privacy-classified attributes? | `opsdir report pii` |
| What has drifted from the intended configuration? | `opsdir report drift` |
| Which applications use the directory, and what should we check about each? | `opsdir report consumers` |
| Which runbooks are out of date? What does nobody own? | `opsdir report stale`, `opsdir report unowned` |
| How does stage differ from production, and why? | `opsdir report overrides` |
| What hidden automation runs (cron, timers, functions, pipelines), and who owns it? | `opsdir report jobs` |
| Which outside services does the platform depend on, which addresses does it send mail from, and where do its events go? | `opsdir report external-services`, `opsdir report mail-senders`, `opsdir report event-streams` |
| What do the servers run beyond the products (OS, Java truststore additions, limits, agents), and on what compute or cluster? | `opsdir report baselines`, `opsdir report compute`, `opsdir report workloads` |
| What is the platform watched for, where do its logs go and for how long (searchable, and in all where a SIEM archives them), and what does each cloud and SIEM actually run? | `opsdir report alerts`, `opsdir report log-routes`, `opsdir report canaries`, `opsdir report monitors` |
| Who records what is done to each environment's cloud, and is the target's trail as complete as the source's? | `opsdir report audit-trails` (CloudTrail, the Activity Log, Cloud Audit Logs: scope, activity, all regions, integrity (validated, or kept in a locked or unlocked immutable store: clouds without log digests protect their records where they export them), where the records go and for how long, who keeps the trail); `opsdir plan` blocks a target with no trail and gives actions where its trail is weaker |
| What watches and assesses each environment's cloud, and does the target keep up with the source? | `opsdir report security-services` (threat detection and the areas it watches, vulnerability scanning, configuration recording, posture against compliance frameworks such as `nist-800-171-r2` and the cloud's own baseline: scope, all regions, where findings go, how long records are kept, who keeps it); `opsdir plan` blocks a target without threat detection or vulnerability scanning, without posture where the source is assessed against a regulatory framework, or without configuration recording where the source exports its history, and gives actions where the target is narrower (blockers where its data is classified `restricted`) |
| Where does each environment's sensitive data lie, and does the target keep looking? | `opsdir report data-discovery` (the stores each data discovery service examines, the organization's own data types it looks for such as CUI markings, how often, where its findings and results go, who keeps it); `opsdir plan` gives actions where the target runs none, leaves a store unexamined, doesn't look for an own data type or keeps findings or results the source sends on (blockers where the target holds controlled data), and where it examines less often |
| Does the target's account allow what its environments need, and is their spending watched? | `opsdir report quotas` (each environment's needs of the provider's limits: vCPUs, public IPs, networks, load balancers, database instances, Kubernetes clusters or a provider quota of its own; what the environments on one account and region need together against the limit fetched from the provider with `opsdir import <cloud>/quotas --run`; the operator's decision); `opsdir plan` gives an action where limits aren't fetched or are below the need, offering the decision as a fix (request the need, request a value of your own, or deny: a denial blocks the move), and renders approved requests where the cloud takes them. `opsdir report budgets` (amount per period, alert thresholds spent and forecast, the channel alerted); the plan gives an action for a target without the source's budget and blocks a budget alerting a channel the target doesn't bind |
| Who reports a cyber incident, to whom and how fast, and do the high-severity findings reach the incident process? | `opsdir report incident-reporting` (each environment's reporting obligations, defined by the estate under `ou=reporting-obligations`, e.g. DFARS 252.204-7012: the hours from discovery to report and to the operator's own incident response, the authority and where reports are filed, who files and the certificate they file with, how long evidence is preserved; and the findings each security service sends to the incident process at or above a severity); `opsdir report reportable-incidents` (each incident under an obligation: discovered, report due, reported, the authority's report number, on time / late / open / overdue); `opsdir plan` blocks a target not held to the source's obligations, held to one no one can meet, whose incident routing is lost (under an obligation) or reaches no one, or whose monitoring records (audit trails, threat detection; retention or immutability lock) are kept shorter than an obligation preserves evidence (an action when a hold runbook is named), and gives actions for a higher severity threshold (a blocker for restricted data) and restricted data held to no obligation |
| What weaknesses are we correcting, which risks has someone accepted, and is a POA&M keeping our CMMC status? | `opsdir report poam` (each known weakness: the controls it concerns as `framework:control`, how and when it was found, scheduled completion and milestones, risk, points, open / overdue / closed), `opsdir report exceptions` (approved deviations: risk adjustment, false positive, operational requirement, risk acceptance, compensating control; the environments they name, the controls and cloud findings they cover, the planner findings they accept, the risk authority, approval, expiry, in force or not), `opsdir report assessments` (score of the maximum, status, the 180-day closeout of a Conditional CMMC status). `opsdir plan` shows the findings an exception in force accepts for the target as accepted (never a broken contract, a key, a reporting obligation, a security service or withheld credentials), blocks an approved exception without approver, risk authority, owner or expiry, a cloud suppression no exception covers, and a POA&M CMMC Level 2 doesn't allow (32 CFR 170.21: requirements never on a POA&M, more than 1 point, a score under 0.8, an expired closeout), and gives actions for expired exceptions, overdue items and the source's exceptions the target has no counterpart for (exceptions never carry over). Each cloud renders and reads back the suppressions carrying exceptions out (AWS: Security Hub automation rules, GuardDuty filters; Azure: policy exemptions, and Defender alert suppression rules through Microsoft's azapi provider when the cloud allows that add-on; Google Cloud: Security Command Center mute rules) |
| Which cloud authorization does each environment rely on, is it enough, and which services and controls fall outside it? | `opsdir import fedramp/cpo FILE` reads a cloud offering's FedRAMP Certification Package Overview (the JSON FedRAMP defines) as the authorization and the services inside its boundary; `opsdir report authorizations` (package, offering, levels, status, services in scope and their date, the environments relying on it) and `opsdir report responsibilities` (who meets each control under an authorization: inherited, shared or the customer, and how). `opsdir plan` blocks a target that must rely on an authorization (a level its obligations require, such as DFARS 252.204-7012's FedRAMP Moderate, a DoD impact level, or restricted data) and relies on none, on one below the level or not certified, uses a service outside its boundary (each cloud names the services an environment uses as its provider's package does), or leaves a control the source's provider covered unmet on the target; and gives actions for a stale in-scope list, a configuration the authorization requires (an Assured Workloads workload, US-person support, IL5 isolation) and a target outside the source's system boundary. `opsdir report regulated-data` lists the regulated data each environment holds (ITAR, EAR, CJIS, HIPAA, IRS 1075); the planner blocks a target that drops what the source holds, and each cloud says where its provider can hold it (AWS GovCloud for export-controlled data, Azure Government or the customer's own encryption, an Assured Workloads folder of the regime) |
| What evidences each control, and can an assessor get it? | `opsdir report evidence` (each control's evidence queries: a report, the change history or a search, its cadence, owner and when it was last collected); `opsdir evidence --boundary <boundary>` writes a system boundary's evidence package (each query's output as CSV and JSON per control, a MANIFEST.json of SHA-256 hashes pinned to a point in the record's history) and, under an approved change, records the run; `opsdir plan` names the target's customer and shared controls no query evidences, stale or missing packages, and the controls whose evidence changes on the target. `opsdir-format-oscal` writes OSCAL 1.2.3 POA&M, SSP control implementations and assessment results from the record and reads OSCAL POA&M and assessment results back (never deleting the record's own items) |
| Who and what may act on the platform, as which cloud identity, under which guardrails, and is it reviewed? | `opsdir report principals`, `opsdir report identities`, `opsdir report guardrails`, `opsdir report access-paths` |
| How does traffic reach the platform, what protects it, and what does each environment's edge and DNS run? | `opsdir report edge-policies`, `opsdir report edge-services`, `opsdir report dns`, `opsdir report header-contracts` |
| How does each environment route out, which private endpoints and endpoint services does it have, and which outside sites may the servers reach? | `opsdir report routes`, `opsdir report private-endpoints`, `opsdir report endpoint-services`, `opsdir report egress-sites` |
| Which managed databases does the platform run on, and are they as available, encrypted, protected and backed up in every environment? | `opsdir report databases` |
| Which cloud-managed identity services does the platform run on or federate with, and can a target's do what its applications use? | `opsdir report managed-identity` (each `ciamManagedIdentity` binding: the service (`cognito-user-pool`, `entra-external-id`), target (it runs one of the platform's identity services, `ciamRealizes`) or neighbour (the partner side of integrations, `ciamPartnerOf`), whom it issues to and relies on (from the integrations' protocol types), who keeps it). `opsdir plan` checks a target against what its cloud's adapter documents of the service: blocks what the vendor documents it can't do (a downstream SAML identity provider on Cognito, the token-exchange grant, a custom issuer), a service the partition doesn't have (Entra External ID in Azure Government) and a published host it can't keep (GovCloud Cognito has no custom domains); blocks what no vendor documentation establishes until the operator answers the unknowns-register question the finding names (its fix proposes it); gives actions for add-ons, per-application MFA, claim transformations, the partition's facts and how users move |
| Are the backup buckets versioned, locked, encrypted, private and copied elsewhere in every environment? | `opsdir report object-stores` |
| When was each part of the record last read back from the live system? | `opsdir report imports` (each set's scopes: `opsdir report import-scopes`) |
| What doesn't anyone know yet, and who must answer it? | `opsdir report unknowns` (the unknowns register: each question, its owner, whether a move waits for it, what it concerns, raised and needed by, open / overdue / answered, the answer). `opsdir plan` blocks on an open blocking question that concerns the source or the target, gives the other open ones as actions dated by when the answer is needed (else the cutover), and lists the answered ones as in place |
| Does every secret reference point at something its store still holds, and which vaulted accounts does nothing reference? | `opsdir report secret-inventory` (each `cyberark://` and `vault://` reference against its store's inventory, metadata only: present, deleted, confirmed missing, listing incomplete, refused, not inventoried; rotation against `ciamRotationDays` only from a timestamp that means rotation, the CPM's status; then the objects nothing references). `opsdir plan` blocks on a target reference confirmed missing or deleted and gives the rest as actions |
| Do the change records agree with the ITSM tickets they are tracked by? | `opsdir report tickets` (each change record linked to its ticket, `ciamTicketRef servicenow:<number>`: the record's status and planned day against what ITSM says, read as evidence by an ITSM add-on such as `opsdir-adapter-servicenow`: the ticket's state, overall approval, planned and actual windows, and the drift: in step, not imported, rejected, cancelled, unapproved, closed while pending, still live though rejected, planned on another day, worked outside its window, the record's own writes under the change outside its window (from the record's history), ticket times later than the read). `opsdir plan` blocks on a change the record approves that ITSM says was rejected or cancelled and gives the rest as actions; a ticket never approves anything in opsdir |
| Which CA issued each certificate, has any been revoked or renewed behind the record's back, and which issued certificates does the record not know? | `opsdir report certificate-authorities` (each CA: who issued its own certificates, its templates, its CRL, OCSP and CA-issuer endpoints, its last inventory) and `opsdir report issued-certificates` (each record certificate against its CA's issued-certificate inventory, metadata only: present, revoked, revocation scheduled, superseded by a renewal, confirmed missing, inventory incomplete or refused; then every active certificate the record holds none of, with its renewal owner). `opsdir plan` blocks on a revoked certificate the record still uses and gives the rest as actions |
| Which outside PKIs (DoD, ECA) do we accept certificates from, under which restrictions, and what changed in their published bundles? | `opsdir report trust-bundles`, `opsdir report trust-policies`; `opsdir plan` proposes a followed bundle's new roots for approval (or decline), flags anchors the publisher dropped and ones expiring within five years, blocks on a bundle whose signed manifest failed, and names client-certificate policies that accept anything their CAs issue or don't check revocation |
| Which CAs do our trust anchors reach through cross-certificates (a bridge, another PKI's root), and which of those cross-certificates expire soon? | `opsdir report cross-certificates` (per anchor, each CA it reaches, the cross-certificates on the way, hops, earliest expiry, policy mappings); `opsdir import x509/certificates` records what certificates say of themselves (typed SANs such as the UPN, key identifiers, basic constraints) and recognises cross-certificates. `opsdir plan` warns about a CA reached only through cross-certificates and about expired or expiring ones. Trust stays with each policy's directly approved anchors |
| Which certificates does a certificate manager renew, watch or report trouble with, and which has it found that the record lacks? | `opsdir report managed-certificates` (each record certificate against the certificate managers' inventories, metadata only: managed, renewed, revoked, disabled, in error, or not managed (never missing: a manager isn't a CA's issuance record); then every certificate in service the managers hold that the record has none of). `opsdir plan` blocks on a certificate the manager says was revoked that the record still uses and gives the rest as actions |
| What does the product a migration retires hold that the target has nothing for? | `opsdir report source-objects` (each object a source product's importer carried because no standard entry holds it, such as SiteMinder's agent and host configuration, trusted hosts, custom sign-on schemes, cookie responses and keys: its type and facts, the server role holding it, how it is handled, whether a move waits for it, its owner). `opsdir plan` gives each one held by a role the target doesn't run as an action, or a blocker when the move waits for it; a source-only adapter adds its own checks (SiteMinder: every realm its agents protect that the target leaves unprotected), and every integration still served by an identity service the target doesn't run blocks until it is re-homed |
| How did each live collection last end, and why did a failed one fail? | `opsdir report collections` |
| How big is the user data, which password schemes does it hold, how many accounts are idle? | `opsdir report data-profile`, `opsdir report data-profile-attributes` |
| Which files copy this server's hostname (or any value), on which lines? | `opsdir report census [<DN>]` |
| Anything else | `opsdir search -b <base> '<LDAP filter>'` |
