# Showcase: operating a fictional estate from the opsdir record

A runnable example of opsdir with real adapter packages. The estate is **Example Aero**, a fictional company whose identity platform (PingDS, PingFederate, PingAM, PingIDM and PingGateway) runs on AWS: production (`source/prod`) and a stage environment (`source/stage`). A second environment on Azure (`target/prod`) is being built, and production will move there; a warm standby on Google Cloud (`standby/prod`) is being built too. The walk-through starts with running the platform from the record; the move is its last chapter. The showcase is the only part of the repository that names platforms outside the adapter packages.

> **All data is synthetic and fictional:** "Example Aero", partners "Skyline Air" / "Harbor MRO", RFC 5737 documentation IPs, the AWS documentation account `111122223333`, made-up resource IDs.

## Run it

```bash
../../opsdir/scripts/dev-install.sh      # once: the core and the adapter packages
./demo.sh                                # the whole walk-through against the local dev database; outputs in out/
../../opsdir/scripts/fetch-tools.sh     # optional, once: Terraform into tools/ (gitignored); demo.sh then also runs
                                         # terraform fmt + validate on every rendered root (or TERRAFORM=/path/terraform)
```

`demo.sh` regenerates `data/` and the directory servers' exports, rebuilds the dev database (`opsdir init`, then `load data/*.ldif`), reads the product exports and the directory servers' configuration and access logs in, asks the record questions, shows the guardrails rejecting bad writes, renders each environment, then plans the move to the second environment, applies the approved changes and plans again.

## What it shows

**Operating the platform**

1. **One record.** Over 400 entries in one database hold the whole platform: servers and bindings per environment, directory configuration and ACIs, consumers, federation integrations and their claims, certificates, keys and secrets as references, owners, runbooks, changes and incidents. Every attribute says what kind of value it is (intent, contract, binding, secret reference, observed, meta: `opsdir report portability`). Each environment declares its stack (`aws`, `azure` or `gcp`, `pingds`, `pingfederate`, `pingam`, `pingidm`, `pinggateway`); `opsdir check` confirms the adapters are installed at acceptable versions.
2. **Product configuration read in.** The partner realm runs on PingAM. Its configuration arrives the way an AM team has it, as an Amster export (`exports/amster`), and `opsdir import --change CHG-2004 pingam exports/amster` reads it into the record under an approved change: the OAuth2 client becomes a standard integration registered with the realm, the sign-in journey (every node and where each outcome leads) and the policy set are held as entries, the OAuth2 provider settings are captured setting by setting, and the SMTP password is withheld. The partner identity sync on PingIDM arrives the same way (`exports/idm`, an IDM project): the directory connector's host becomes the `ds-ldaps-service` role and its bind account is linked to the `idm-sync` consumer record, so each environment renders its own host; its credentials are withheld until an approved change (CHG-2005) names the secret roles they come from. The partner portal's PingGateway route (`exports/ig`) signs partner staff in with the AM realm: on import it is linked to the `partner-portal` client the Amster import recorded and to the realm's issuer. And what the production directory servers actually run arrives as their own files: a copy of each server's `config/` directory (`exports/ds-config/<hostname>/config.ldif`, and for ds-2 an archived configuration the server saved before a change), read in by `opsdir import --change CHG-2006 --at 20260920030000Z pingds/config exports/ds-config` as dated snapshots of each server. Who uses the directory comes from its access logs: three days of each server's JSON access log (`exports/ds-access-logs`), read by `opsdir import --change CHG-2007 pingds/access-log exports/ds-access-logs`. PingFederate's configuration arrives as its Admin API bulk export (`exports/pingfederate/data.json`), read by `opsdir import --change CHG-2008 pingfederate/bulk exports/pingfederate`: the connections and clients match the record, so the one change is a client PingFederate has that the record didn't (`reports-api`, now listed as unowned); its two data stores are recorded too, each with its credentials withheld until CHG-2005 names their secret roles, and the import points out that the LDAP data store reaches ds-1 by its hostname next to the LDAPS service name, so that store has no single service name each environment can render (an action in the plan); its grant store reaches the grant database, which each environment runs as a managed database (below), so the import names the database's role (`pf-grants-db`) and each environment renders its own endpoint. The export also carries the sign-in setup: a password credential validator on that data store, the HTML Form adapter that uses it, a policy contract and the default authentication policy's tree, the token manager with the OIDC policy and scopes the clients use, and a server-settings resource held as is; each is linked to what it names, and the planner checks the links. The PingFederate nodes' own files (`exports/pingfederate-nodes`: run.properties, tcp.xml, hivemodule.xml), read by `opsdir import --change CHG-2008 pingfederate/node-files exports/pingfederate-nodes`, put each node's mode, tags and ports on its server, show the cluster finds its members through an S3 bucket (the source's `pf-cluster-discovery` binding; `pingfederate/cluster/jgroups.properties` renders it per environment) and that OAuth clients and grants live in the JDBC grant store. The target binds no cluster discovery: a planted blocker, since every node's tcp.xml is cloud-specific. The platform's hidden automation arrives the same way: copies of a few servers' scheduler files (`exports/hosts`, read by `opsdir import --change CHG-2010 linux/jobs exports/hosts`) show ds-2 running the MRO nightly export from cron (and only ds-2, which the import points out) and both PingFederate engines shipping their audit log from a systemd timer, each linked to the ops-scripts bundle it runs; the ciam-ops repository's GitHub Actions workflow (`exports/pipelines`, `github-actions/workflows`) adds the nightly directory backup with its schedule, runners, environment and the secret it names. `opsdir report jobs` lists them; nobody owns them yet (three actions in the plan, until approved change CHG-2011 names their owners). The same servers' own files (os-release, Java runtime and `keytool -list` of its truststore, limits, sysctl, packages, service units, `/etc/hosts`; one server or more of every role) give each server role its host baseline (`opsdir import --change CHG-2012 linux/baseline exports/hosts`, `opsdir report baselines`): the import names ds-3's lower `somaxconn` and pf-engine-2's newer Java patch as drift, and the plan names what a rebuild would lose: ds-2 pins a legacy reports host to its address in `/etc/hosts`, and the PingFederate servers' truststore adds the corporate root CA, which the record doesn't hold (two actions, until approved change CHG-2013 records the CA and links it). PingFederate's bulk export also holds its SMTP notification publisher and reCAPTCHA provider: plugin instances with their secrets withheld (two blockers until CHG-2005 names their secret roles), and the record's view of the services outside the platform (`opsdir report external-services`, `mail-senders`, `event-streams`): the SES SMTP relay, the address reset mail comes from and the identity audit stream the SIEM reads. The source sends as example-aero.test from a verified SES identity (DMARC reject); the target's Communication Services domain isn't DKIM-verified yet and its DMARC is weaker (a blocker: reset mail would land in spam; and an action), and no bus carries the audit stream in the target (a blocker). Each environment's compute groups are bindings like any other (`opsdir report compute`): the engines run in an autoscaling group over two zones in the source and in a scale set in one zone in the target, a planted action. Finally the census (`opsdir census --change CHG-2009 exports/census`) scans a few of the platform's files for values of the record: a nightly export script on ds-2 and `/etc/hosts` on pf-engine-1 both hard-code ds-1's hostname and address, and the customer portal's configuration names the LDAPS service (fine, as long as the name is kept) next to a password written into the file, flagged by line and never stored. `opsdir report census cn=ds-1,...` lists every file and line that copies ds-1's values; the plan asks for the two files to change before the move (and for the portal's too, until CHG-2003 restores the LDAPS name). The importer records what each consumer does (where it connects from, its operations, the attributes it reads, unindexed searches, whether it uses TLS, its peak rate) next to what its operators recorded (owner, criticality, migration status, last review), without reading a filter or a value: the end users PingFederate checks passwords for are counted, not recorded.
3. **Questions become queries.** Certificates by expiry, the blast radius of a partner's signing certificate, who can read privacy-classified attributes, the consumers to review (`opsdir report consumers`: each one's owner, status, TLS, unindexed searches, when last seen and reviewed, and what to check: here the legacy report account has no owner, uses plain text, searches unindexed and reads high-PII attributes, and the portal's review is over a year old), and LDAP filter searches over the record.
4. **Keys and secrets as data.** Every key and secret is a credential entry (what it is, how it rotates, whether another environment must receive the same material) bound per environment to where it is kept: Secrets Manager and KMS in AWS, Key Vault in Azure, Secret Manager and Cloud KMS in Google Cloud, with a CyberArk copy of the directory root password. `opsdir report keys source/prod` shows production's key placement (the directory root password's rotation is overdue), `report credentials` the sprawl, and `report rotation-impact` everything rotating the signing key touches (every environment's secrets, its certificate and every application that trusts it).
5. **Custom fields and record types.** The operator defines `xCostCenter` (on owners), `xDataResidency` (on environments), `xTokenLifetimeMinutes` (on integrations) and a `xFeatureFlag` record type with its own fields, as entries with their metadata; `opsdir report custom` shows each and where it is used. Config files are held in the record setting by setting (`report capture`) and rebuilt from it for any environment (`opsdir file run.properties --env source/prod`); code and templates deployed as they are are recorded by repo path and hash (`report bundles`).
6. **Drift and hygiene.** Each server's imported configuration is compared with the declared one (`opsdir report drift`): a missing index on ds-2 (the cause of incident INC-2231; ds-2's archived configuration, saved on 2026-09-12 22:40, still has it, which dates the unrecorded change), an unrecorded index and a changed lockout threshold on ds-3. Also stale runbooks (the index runbook after the mail index change, and the SAML onboarding runbook, whose signing certificate the PingFederate import updated with its key pair id), and PII readable by an unowned legacy account. And what the clouds actually run against the record, without changing anything (`--dry-run`): the source's Terraform state (`exports/cloud/source/prod/terraform.tfstate`, `opsdir import --dry-run aws/terraform-state exports/cloud`) shows pf-engine-2 resized in the console and the disk key's automatic rotation switched off, and names an untagged bastion instance and a hand-opened "temporary vendor access" rule nobody recorded; the second environment's Azure CLI output (`exports/cloud/target/prod/`, `opsdir import --dry-run azure/cli-inventory exports/cloud`) shows ds-3 resized and fw-idm-sync's NSG priority changed in the portal, and a management subnet added there, which its role map (`roles.json`) names `subnet-mgmt`; the standby's Cloud Asset Inventory export and `gcloud` output (`exports/cloud/standby/prod/`, `opsdir import --dry-run gcp/cli-inventory exports/cloud`) shows ds-2 resized in the console and names an SSH rule for IAP opened by hand, its health-check rules left out as part of the load balancers and its secrets, which Secret Manager lists by project number, read as the project's ID. Each change is listed with what it sets. Settings every server has from setup (the default and root password policies, the LDIF handler, the error and debug loggers) are declared too, and `dsconfig.batch` sets them rather than creating them. And the shape of the production user data, without copying it: `opsdir data-profile` reads the directory's data as ldapsearch prints it (`exports/ds-data/source-prod.ldif`, 255 entries), with the estate's own terms (`--term last-login=lastLoginTime`, `kba=challengeAnswer`, `pending`/`disabled` from `registrationStatus`), and writes counts only (`out/data-profile/source-prod.json`, CHG-2014 records it; `opsdir report data-profile`). The planner then names 24 password hashes in a scheme no policy uses (SSHA512, from the old portal), two attributes without a user-schema record (`cn`, and `crmContactId` a CRM integration writes), a group member pointing at a deleted supplier, and 37 accounts still holding challenge answers. What the platform is watched for is intent too (`opsdir report alerts`, `log-routes`, `canaries`): a replication-lag and a login-failures rule paged through each environment's alert channel (an SNS topic, an Azure action group), audit logs that must be kept 400 days under legal hold, and a synthetic SSO sign-in. What each cloud runs of it is recorded per environment (`opsdir report monitors`), and the source's Terraform state shows it with one alarm someone added in the console. The planner names the target's audit workspace keeping logs only 90 days, a disk-space alarm the source runs that no rule describes (and the target doesn't run), a rule without a runbook, and the legal hold the source's log group must outlive.
7. **Guardrails enforced by the database.** An unapproved change, deleting a certificate still in use, a secret value in a reference field, and a missing required attribute are all **rejected**. Every accepted write is kept in history under its change (`opsdir history`).
8. **Environments as overlays.** `source/stage` is an overlay of `source/prod`: it shares production's network, subnets, egress, disk key and firewall rules (but not the consumers'), and has its own servers, service names, secrets and backups. It overrides three shared values (one directory replica, a higher lockout threshold for test automation, short tokens for one application), so its `dsconfig.batch` differs from production's only there; `opsdir report overrides` lists them with why, and its MANIFEST records them. Environments also declare roles they must bind as data (`ciamRequiredRole`).
9. **A warm standby on a third cloud.** `standby/prod` is being built on Google Cloud. Its directory replicas join production's deployment over a VPN (their setup scripts bootstrap from the AWS replicas; secrets are resolved with `gcloud secrets versions access`), its network and subnetworks are the landing zone's Shared VPC (read as data), its firewall rules target each server role's network tag with pinned priorities, each service name is a passthrough load balancer with the firewall rule Google's health checks need, and PingFederate's nodes find each other by TCPPING, listed from the record (Ping documents no Cloud Storage protocol). The directory, ACI, federation and realm files render as for the other environments; `opsdir report keys standby/prod` shows where it keeps each key.

10. **Who may act on the platform.** What may be done is intent, the same everywhere: permission sets name verbs on binding roles (`read-secret pf-admin-password`, `use-key disk-encryption`, `write-storage backup-target`, `manage pf-sso-service`), so one set means each environment's own secret, key or bucket; principals hold them: PingFederate's and the directory's servers (workloads), the ciam-ops pipeline (a deployer), the platform admins (operators, with MFA and just-in-time elevation) and the break-glass account, each with an owner and a review date (`opsdir report principals`). Each environment binds the cloud identity each principal acts as, with what the cloud grants it in its own terms (`report identities`): IAM roles in AWS, managed identities and an Entra group in Azure, service accounts and a Google group in the standby; the organization guardrails over it (`report guardrails`) and the ways operators come in (`report access-paths`). The renderer writes each workload's least-privilege identity into the platform's Terraform, and what the landing zone keeps (the pipeline's OIDC trust, the admins' Identity Center permission set, Entra PIM eligibility or Google group access, and the guardrails as service control policies, policy assignments or organization policies) into `terraform/landing-zone/` for the landing zone team, plus `access/evaluate.sh`, which asks the AWS policy simulator or Google's Policy Troubleshooter about every permission for the import to record. The source's IAM arrives the same way as the rest of the cloud: its Terraform state and the landing zone's (`exports/cloud/source/prod/landing-zone.tfstate`) show PingFederate's role given `secretsmanager:ListSecrets` on everything in the console, and name the break-glass role's AWS managed policy, which a state doesn't hold. The planner judges each permission allowed, denied or unknown, and names what's planted: the directory's role may do anything in S3, the admins' review is over a year old and the break-glass account was last tested eleven months ago, an IDM role nobody records as acting as it (and the target doesn't bind), the target's guardrails don't stop audit logs being disabled and operators can't come in by a session manager there (a request to the landing zone team, `requests/cloud-landing-zone.md`), and in the target the admins' Key Vault rights are PIM-eligible only, so whether they may manage the keys can't be told until activated.

11. **How traffic reaches the platform.** The edge is intent too (`opsdir report edge-policies`, `header-contracts`): sso and login terminate TLS at the edge and re-encrypt to their servers (TLS 1.2, intermediate ciphers, cookie stickiness) behind a web application firewall (managed core rules, known bad inputs and bots; rate limits on sign-in and tokens, aimed at the endpoints PingFederate and PingAM declare; the SAML response excluded from the core rules; network DDoS protection); LDAPS passes through. Two header contracts: the client's address the sign-on load balancers pass on, and the partner user the gateway puts in a header for the partner portal. Each cloud renders it its own way: an ALB with a WAFv2 web ACL and Shield in the source, an Application Gateway with a WAF policy and its certificate read from Key Vault in the target, a regional Application Load Balancer with Cloud Armor in the standby. What each environment publishes and resolves is bound too (`opsdir report dns`): the public zone is on the corporate DNS team's Infoblox, so the clouds render no record into it; the private zone, the AD domain's forwarder, the SSO certificate in each cloud's store. What the source's load balancers run today is read back from its Terraform state as facts in the same terms (`opsdir report edge-services`). The planner names what's planted: the public names' 3600 s TTLs, to be lowered by a date ahead of cutover, and a drafted request to the corporate DNS team to repoint them (`requests/corporate-dns.md`); PingFederate's self-service password reset with no rate limit; the gateway's source load balancer keeping clients on one server by source address, which no policy states; a partner header a client could send itself; sso and login moving from passthrough to TLS termination, so PingFederate and PingAM must trust the load balancers' client-address header; and the AD domain forwarded in the source and not in the target (a blocker, until approved change CHG-2015 adds the forwarder).

12. **The network under it.** Each environment's network depth is bound like everything else (`opsdir report routes`, `private-endpoints`, `endpoint-services`, `egress-sites`). That covers route tables and the subnets that use them, network ACLs, flow logs and where they go, private endpoints to the secret stores and cloud APIs, the endpoint service exposing LDAPS to the supplier portal's network, the egress firewalls and forward proxies with the sites they let the servers reach, and the links to other networks. What the stack runs renders into its own Terraform. The plumbing the landing zone keeps (NAT, route tables, ACLs, flow logs) renders into `terraform/landing-zone/`, and what another team keeps goes into that team's folder (`terraform/landing-zone/network-security/`). Each comes with an import block when it already exists, and a request to its keeper when it doesn't (`requests/network-security.md`). The planner names what's planted:
    - the supplier portal must reconnect to the target's Private Link Service and be accepted;
    - the hub firewall doesn't allow the mail relay;
    - the products aren't told about the hub's forward proxy;
    - the target's route table sends internet traffic straight to the NAT gateway, around the hub firewall whose domain rules the stack relies on;
    - its flow log keeps 14 days where the source keeps 30;
    - the source's network ACL on the directory subnet has no counterpart in Azure (a blocker: decide, and record why).
13. **The databases it runs on.** PingFederate's grant store is a managed PostgreSQL database each environment runs by role (`opsdir report databases`): RDS in the source (PostgreSQL 16.4, Multi-AZ, TLS required, 14 days of backups with point-in-time restore, deletion protection, the platform's key), a smaller single-zone instance of its own in stage, a Flexible Server in its own delegated subnet in the target and Cloud SQL in the standby. Each admits PingFederate's subnets to its port: on AWS the database's own security group carries the rules, in the target a network security group on its delegated subnet, and in the standby the private services access peering carries the traffic (Cloud SQL's address is in Google's network, where no firewall rule reaches), whose range the network team keeps and renders in their root, and which the standby's egress rules admit among its private ranges. Each renders into its cloud's Terraform with its subnet and parameter groups or configurations, its key, and its administrator password in the secret store only (RDS keeps it in Secrets Manager; Azure and Google Cloud write it write-only from an ephemeral read of the secret), and each cloud's export reads it back without drift. A move keeps the engine and its major version (an upgrade is its own change) and everything the database had; the planner names what the target was set up without: no zone-redundant standby, backups kept 7 days where the source keeps 14, and no deletion protection (until approved change CHG-2016 keeps the backups 14 days and locks the server). The directory's backup buckets say how they keep the backups too (`opsdir report object-stores`): the source's S3 bucket is versioned, locked in compliance mode for the backups' 35 days (nobody, the account's root included, can delete one sooner), encrypted with the platform's key, closed to the public, moved to a colder tier after 30 days and deleted after 90, and replicated to a bucket in us-west-2; the standby's Cloud Storage bucket the same way but for the copy (Cloud Storage has no replication setting). Each renders as the cloud's bucket with each setting (S3's as their own resources, Cloud Storage's retention policy and lifecycle rules), adopted by an import block, and reads back without drift. The target has no backup target (a blocker) until approved change CHG-2017 adds a container in a storage account the stack keeps, and lets the directory servers' identity write to it; copied from the stage template, it has no immutability policy and nothing copies it to another region (two actions it raises, each with a fix).
14. **Reading the clouds back.** `opsdir import --dry-run` reads each cloud's export (the source's Terraform state, the target's Azure CLI output, the standby's Cloud Asset Inventory) as drift. Where the live system and the record disagree, it lists a **conflict** with a key: the source's disk key rotation (record `TRUE`, live `FALSE`), an instance size, a firewall priority. Applying the import is refused until each conflict is decided, either taking the live value (`--take`) or keeping the record's (`--keep`); neither side is assumed right. Every applied import records when it read each environment (`opsdir report imports`).

**Moving production to a second environment**

15. **One record, two clouds.** The directory configuration, ACIs and PingFederate configuration render **byte-identical** for AWS and Azure, and so do the standard files the products build on: the user directory's schema and tree as standard LDIF, SAML metadata of every partner and of the platform's own IdP, OIDC client registrations and the discovery document, and the PingAM realm. Only Terraform and the per-server setup scripts differ, and the Google Cloud standby renders the same files too (its PingFederate discovery and `run.properties` are its own). (A test renders the same record as OpenDJ instead of PingDS: the standard files and ACIs are identical, the product files are OpenDJ's.)
16. **Continuity.** The Azure replicas' setup scripts bootstrap from the AWS replicas, so they **join the existing directory deployment** (same deployment ID, so encrypted data and backups stay readable). Secrets are resolved at run time from references (`aws secretsmanager …` vs `az keyvault …`).
17. **The planner finds what blocks cutover.** The estate is **deliberately broken**: the problems are planted by the fixture in `example_estate/` (written out by `scripts/gen-synthetic.py`) and listed in `data/expected-findings.json`, so "NOT READY, 23 blockers" is the *correct* result. It finds a changed service name (contract break), missing firewall rules and backup target, untested or unowned consumers, certificates expiring before cutover, keys the target keeps wrongly (the disk key needs an HSM but the target vault protects it in software; the PingFederate signing key must be carried over, not regenerated; the target drops automatic rotation), the IDM connectors' and PingFederate data stores' missing secret roles, the HR database connector and PingFederate's data stores that reach the same host from every environment, PingFederate's cluster discovery the target doesn't bind, a grant database the target keeps less available and less protected, **other parties' allowlists** that pin old addresses, files that hard-code the source's hostnames and addresses (from the census), what the servers run beyond the products (names pinned in `/etc/hosts`, truststore additions the record lacks, compute spread over fewer zones), and what the platform depends on outside itself (mail the target can't deliver yet, an event stream nothing carries), and who may act on it (a role the target doesn't bind, a grant wider than its permissions, an overdue review, a stale break-glass test, a guardrail and a way in the target lacks, rights that are only eligible). Each has an owner and a do-by date from its lead time, plus a drafted request to each party. `scripts/check-findings.py` checks the planner against that list before and after the changes: every planted problem detected, nothing unexpected, and the fixed ones gone.
18. **Fixing what it finds.** Where a finding has a known record change, the plan offers it as a fix (`opsdir fix list`, `fix show`), and a person approves it. Some fixes are exact: the stable LDAPS name, the ports gap, the proxy keys linked to the proxy binding, the target's flow-log retention, the grant database's backups, standby and deletion protection carried over, the backup container's lock. Some are a choice: the secret role behind each withheld credential is offered as a pick list and never guessed. Some take values only the operator knows: a role the target lacks becomes a template of the source's binding, with the target's own references as inputs, and a fixed host such as the HR database in IDM's JDBC URL or the partner app becomes an external system under a role you name (the corporate directory's two domain controllers become two hosts of one role, in their order). Some wait for something first (pinning firewall priorities waits for a fresh import), and some are confirmed only by a later import (lowering the public names' TTLs). Proposing writes a change record holding the exact records; the store checks them first and refuses them until a person approves.
19. **Changes as entries.** Approved changes (LDIF records) produce exactly the expected diffs: a new network security rule and a DNS name fix in the Terraform, the secret roles of the IDM connectors and PingFederate's data stores (CHG-2005), the owners of the imported jobs (CHG-2011), the corporate root CA the PingFederate servers trust (CHG-2013), the AD domain's forwarder in the target (CHG-2015), the grant database's backups and deletion lock (CHG-2016), and the target's backup container (CHG-2017), which also brings the two findings about it. Blockers go from 23 to 12, actions from 69 to 62.

`opsdir migrate source/prod target/prod` runs the whole move (check, plan, render); `opsdir migrate target/prod source/prod` runs it the other way, rendering the AWS environment from the same record.

## What's verified, and what isn't

| Verified | Not verified |
|---|---|
| Rendered Terraform passes `terraform fmt -check` and **`terraform validate`** against the `hashicorp/aws ~> 5` and `hashicorp/azurerm ~> 4` provider schemas | No `plan`/`apply` against real accounts (fictional IDs) |
| Every database rule (schema, references, change governance, secret references, vocabulary) exercised | `dsconfig` / `setup` flags follow the PingDS 7.x documentation but haven't been run against a real PingDS |
| LDIF round trip (load, export) and change sets (diff, apply) | PingFederate JSON is an illustrative subset of Admin API shapes, not validated against a live Admin API |
| | The schema file has not been loaded into a real LDAP server; OpenDJ `setup`/`dsreplication` flags follow the OpenDJ 4.x documentation, unrun |
| | SAML metadata and OIDC documents are schema-shaped but not yet loaded into a real SAML/OIDC product |

## Layout

```
example_estate/     the estate as pure builders, one module per part of the stack (build() composes them)
data/               the generated LDIF (556 entries) and expected-findings.json
changes/            approved change records; changes/rejected/ = writes that must fail
golden/             the accepted snapshot of every command's output
scripts/            gen-synthetic.py, check-findings.py, snapshot-outputs.sh
tests/              showcase tests: unit (the estate in memory vs golden) and integration (Postgres snapshot,
                    workspaces, upgrades with real data)
exports/            product exports read in by importers: amster/ (PingAM), idm/ (PingIDM), ig/ (PingGateway),
                    pingfederate/ (an Admin API bulk export), census/ (servers' and applications' files); ds-config/ (each production directory server's config/
                    directory), ds-access-logs/ (three days of their JSON access logs) and cloud/ (the source's Terraform
                    state, the second environment's Azure CLI output and role map) and ds-data/ (the production
                    directory's user data, as ldapsearch prints it), all generated with data/
demo.sh             the walk-through
```

## Checking a change

The showcase tests run with everything else (`../../opsdir/scripts/test.sh` from anywhere). The unit tests build the estate in memory with the store's own preparation functions; its renders, plans, findings, drift, searches and export must equal `golden/` byte for byte, before and after the approved changes. The integration tests run `scripts/snapshot-outputs.sh` against Postgres (`opsdir_test`) and compare every captured output with `golden/`, one test per file, and check the guardrails directly.

To snapshot by hand: `OPSDIR_DSN=... scripts/snapshot-outputs.sh /tmp/snap && diff -r golden /tmp/snap`. The script regenerates the published schema, `data/`, `exports/ds-config/`, `exports/ds-access-logs/` and `exports/cloud/` (they must reproduce the committed files), then runs every command on a fresh load. A refactor must leave the diff empty; an intended change of output is reviewed, then the snapshot replaces `golden/`. It drops and reloads the `opsdir` schema in the target database.
